FetchXML Builder — TypeScript greenfield roadmap

A modern, web-first FetchXML workbench built on React, TypeScript, and the Dataverse Web API.

Platform-agnostic from day one. The XrmToolBox fork is a reference quarry for domain logic, schema assets, and test cases — not a compatibility target. The first deliverable is the Power Automate parameter converter, built as a pure, fully-tested library function.

Framework React 19 + Vite
Language TypeScript (strict)
Auth MSAL Browser / PKCE
Desktop Tauri (Phase 5)

Executive Overview

The current repository is a .NET Framework 4.8 XrmToolBox plugin. It holds genuine value as a source of domain knowledge: the FetchXML schema, converter algorithms, autocomplete behavior, and integration test ideas. None of that is a reason to stay on .NET.

The greenfield approach uses a pnpm workspace monorepo with two packages and one app. packages/core is pure TypeScript with zero framework dependencies. packages/dataverse owns all Dataverse Web API and MSAL concerns. apps/web is the React + Vite front end that consumes both.

First deliverable: the Power Automate parameter converter as a pure function in packages/core, covered by Vitest golden snapshot tests, before any UI work begins.
Legacy code is a quarry Core has zero deps Golden tests first Web API over SDK Desktop is a wrapper

Architecture

Three units with clear dependency direction. The web app is a consumer, not the core.

Reference

Existing Fork

XSD schema, converter algorithms, autocomplete behavior, sample workflows, and test cases to harvest selectively. Never imported at runtime.

Core

packages/core

Pure TypeScript. FetchXML parser, formatter, validator, all converters including Power Automate and OData, neutral DTOs. Zero framework dependencies.

Dataverse

packages/dataverse

MSAL browser auth, Dataverse Web API client, metadata cache, saved views, FetchXML execution, paging, and result normalization.

Web

apps/web

React 19 + Vite SPA. Monaco XML editor, visual query builder, metadata browser, converter panels, results grid. Consumes both packages.

Dependency rule: packages/core imports nothing external. packages/dataverse imports core and MSAL only. apps/web imports both packages and all UI dependencies. This direction never reverses.

Priority Feature: Power Automate Parameter Converter

This is the highest-value converter and the first unit of real logic to ship. It takes a FetchXML document and replaces hardcoded filter values with Power Automate @{parameters('…')} expression tokens, producing a parameterized query ready to drop into a flow action.

It lives entirely in packages/core/src/converters/toPowerAutomate.ts and has no UI dependency. The function signature is stable before the first React component is written.

Build order: write the golden snapshot tests first, then implement the converter until tests pass. UI panels come later and simply call this function.
Converter shape

What the function covers

  • Detect literal values in <condition> elements
  • Infer parameter names from attribute and entity context
  • Emit @{parameters('…')} tokens in place of values
  • Return a parameter manifest alongside the converted XML
  • Support value type hints: string, integer, datetime, guid, boolean
  • Preserve structure and formatting of the source query
  • Accept an optional name override map for custom parameter names

Phased Timeline

Phase 0 Now

Plan and inventory

Commit this roadmap. Classify every file in the fork as copy, adapt, or ignore. Scaffold the pnpm workspace with three empty packages. Configure Biome, Vitest, and TypeScript strict mode.

Phase 1 Core

Power Automate converter and core library

Implement the Power Automate parameter converter first with Vitest golden snapshots. Add the FetchXML parser, formatter, validator, and OData converter. Port the fetch.xsd and autocomplete logic. All covered by golden tests before the web app scaffolding begins.

Phase 2 Web shell

Offline editor and converter panels

Scaffold apps/web with Vite, Tailwind v4, shadcn/ui layout, and TanStack Router. Wire Monaco editor, visual query builder, validation markers, and all converter output panels. The full offline experience works before any Dataverse connection exists.

Phase 3 Auth + API

MSAL auth and live Dataverse access

Build packages/dataverse: MSAL PKCE flow, org URL setup, metadata cache, entity and attribute browser, saved view loading, FetchXML execution, paging, and result grid. Add mocked integration tests and keep real-org tests behind environment variables.

Phase 4 Polish

Hardening and Playwright E2E coverage

Add Playwright tests for the editor, query builder, converter panels, and result grid flows. Fix rough edges from real usage. Add query history, favorites, and import/export polish. Performance and bundle audits.

Phase 5 Desktop

Tauri desktop packaging

Wrap the proven web app with Tauri for macOS and Linux. The browser and PWA remain the canonical experience. Desktop adds native file system access for query export and offline metadata packages.

Rule

Golden tests gate converter changes

Any change to converter output requires a deliberate snapshot update. This protects important behavior without requiring identical output to the legacy fork — intentional differences are accepted but must be explicit.

Risks and Controls

  • Metadata shape differences: Dataverse Web API metadata is not identical to the .NET SDK types. Build fixture files from real org responses early and use them in all metadata-dependent tests.
  • MSAL and CORS configuration: requires an Entra app registration, correct redirect URIs, and org URL validation. Set this up in Phase 3 before any live data work begins.
  • Monaco autocomplete integration: feeding the XSD to Monaco's XML language service requires a configuration step that is not straightforward. Spike this early in Phase 2 before building the full editor panel.
  • Converter behavior drift from the fork: intentional differences are acceptable. Golden snapshot tests make every divergence visible and explicit rather than silent.
  • Scope creep on the visual builder: the query tree is the most complex UI component. Keep it read-only in Phase 2 if needed — formatting and converters ship first.
  • Tauri compatibility: MSAL PKCE redirect flow needs custom URI scheme handling in Tauri. This is solved but not trivial. Confirm the approach before committing to Phase 5.

Assumptions and References

Assumptions

  • No compatibility obligation to the XrmToolBox plugin format or its host.
  • No server-side component. All auth uses MSAL PKCE browser flows.
  • Dataverse access targets the Web API only — no .NET SDK at runtime.
  • The XrmToolBox fork is maintained separately and is not part of this product's release.
  • Desktop packaging is optional and comes only after the web experience is stable.
  • The Power Automate parameter converter is the highest-priority deliverable in Phase 1.
